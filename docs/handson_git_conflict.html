1. 学習目標

  • featureブランチの作成からPull Request（PR）作成・レビュー・マージまでの一連の流れを体験する
  • 複数人が並行して同じファイルを変更したときにコンフリクトがなぜ・どこで発生するかを理解する
  • git rebase によるコンフリクト解消と、git merge との違いを説明できるようになる
  • git push --force-with-lease の必要性と、単純な --force との危険性の違いを理解する
  • 組み込み開発現場で起きがちな「同一関数のロジック競合」「ヘッダ/構造体定義の競合」「相手の変更がローカルに反映されていない」ケースへの対処を体験する

2. 全体の流れ（ブランチ図）

multiBranch_test を起点に、開発者A・開発者Bがそれぞれ独立したブランチで作業し、Aを先にマージ、Bはリベースでコンフリクトを解消してからマージする流れです。

gitGraph commit id: "multiBranch_test-start" branch "dev-a-battery-hysteresis" branch "dev-b-battery-overvoltage-latch" checkout "dev-a-battery-hysteresis" commit id: "A-impl-hysteresis" checkout main merge "dev-a-battery-hysteresis" id: "PR-A-merged" checkout "dev-b-battery-overvoltage-latch" commit id: "B-impl-overvoltage-latch" commit id: "B-rebase-resolve-conflict" checkout main merge "dev-b-battery-overvoltage-latch" id: "PR-B-merged"

実際のブランチ名は dev-a/battery-hysteresis / dev-b/battery-overvoltage-latch ですが、Mermaidのgraph表示の都合上ハイフン区切りで表記しています。git rebase はコミット履歴を書き換える操作のため、上図の「B-rebase-resolve-conflict」はBのブランチの履歴がAのマージ後のmultiBranch_testの上に付け替えられたことを表しています（マージコミットとは異なる仕組みです）。

3. 事前準備

受講者向けチェックリスト

  • リポジトリをclone済みで、multiBranch_test ブランチが最新であること
  • cmake / ninja（または ctest）でビルド・テストが実行できる環境
  • VS Codeでリポジトリを開いていること（Git機能は標準搭載、追加インストール不要）
  • （任意・推奨）拡張機能「GitLens」をインストールしておくと、コミットグラフの右クリックメニューから fetch・rebase・merge などをより視覚的に操作できる
  • GitHubアカウントでリポジトリにアクセスでき、ブラウザでPR操作ができること
  • 1人で演習する場合は「開発者A」「開発者B」の2役を演じる想定（実務では別々の担当者が同時に行う）
本教材の操作方針: 各手順はVS Codeのソース管理（Source Control）ビューとGitHub.comのWeb画面によるGUI操作を主として説明します。あわせて「対応するコマンド（参考）」として同じ操作を行うgitコマンドも折りたたみ表示で併記するので、GUIの裏で何が実行されているかも確認できます。
重要: 開発者Bのブランチは、開発者Aのマージ前の multiBranch_test から分岐させてください。これにより「相手の変更がローカルに反映されていない」状態を意図的に再現します。

開発者A Step A-1: ブランチ作成と実装

🖱 VS Code操作
  1. ウィンドウ左下のステータスバーに表示されているブランチ名（例: multiBranch_test）をクリックする

開発者B Step B-1.5: コンフリクトに気づくタイミング

開発者Bは、この時点ではまだ何もおかしいことに気づいていません。ローカルのビルド・テストは問題なく通り、自分のPR (#7) もエラーなく作成できているためです。気づくきっかけは主に次の2つです。

  1. GitHub PR画面での気づき: 開発者AのPR (#6) がマージされた直後、PR #7 のページを開くと GitHub が自動的に This branch has conflicts that must be resolved（このブランチにはマージ前に解決が必要なコンフリクトがあります）という警告を表示します。これはBが何も操作していなくても、GitHub側がベースブランチ（multiBranch_test）とBのブランチを比較して検知するものです。
  2. VS Code上での気づき: ソース管理ビューの「...」メニュー→「プル」を実行しようとすると、VS Codeが「リモートに新しいコミットがあります」と表示し、さらに取り込もうとするとコンフリクトが検出されます。
github.com/…/pull/7●●●
✕ This branch has conflicts that must be resolved
⇄ src/dbc/battery_monitor.c, src/app/temp_alarm_fsm.h
Merge pull request（無効化）
体験ポイント: ここで「自分は何も壊していないのに、なぜ急にPRが赤くなるのか？」を実際に確認させてください。原因は自分の変更ではなく、ベースブランチが自分の知らない間に進んでいたことにあります。組み込み開発では「相手の変更に気づかないままローカルで作業を続ける」ことが最も典型的なコンフリクトの温床です。

merge か rebase か、この教材で rebase を選ぶ理由

選択肢内容この教材での採用
git merge origin/multiBranch_testBのブランチに、multiBranch_testを取り込むマージコミットを作る。履歴が分岐したまま残る。他の人ともBブランチを共有している場合はこちらが安全（履歴を書き換えないため）
git rebase origin/multiBranch_testBのコミットを、最新のmultiBranch_testの上に「付け替える」。履歴が一本の直線になり、PRの差分もBの変更だけに見える。採用。Bのブランチは自分専用（他の人がpullしていない）ため、履歴を書き換えても安全。PRのdiffが読みやすくなるメリットを優先
判断基準: そのブランチをまだ自分しか使っていないかがポイントです。誰かが既にpullして作業している共有ブランチをrebaseすると、相手の履歴と食い違い、二次的なコンフリクトを引き起こします。featureブランチのような「個人の作業ブランチ」はrebase、共有ブランチはmergeが基本方針です。

開発者B Step B-2: リベースしてコンフリクト解消を体験する

🖱 VS Code標準機能での操作
  1. コマンドパレット（Ctrl+Shift+P）を開き、「Git: Rebase Branch...」と入力して実行する
  2. リベース先として origin/multiBranch_test を選択する
  3. コンフリクトが発生すると、ソース管理ビューに「マージの変更」という区分で battery_monitor.c と temp_alarm_fsm.h が表示される
  4. ファイルをクリックしてエディタを開くと、コンフリクト箇所の上に「現在の変更を承諾」「入力側の変更を承諾」「両方の変更を承諾」というインラインのボタン（CodeLens）が表示される。今回は両方の変更を残したいので「両方の変更を承諾」を選ぶか、手動で編集してマーカーを削除する
  5. 解消したファイルを「ステージ済みの変更」に追加（ファイル横の「+」をクリック）
  6. ソース管理ビュー上部の「...」メニュー→「続行 (Continue)」でリベースを完了する
  7. ビルド・テストを実行して問題ないことを確認
  8. ステータスバーの「↑n（強制プッシュが必要）」表示部分をクリックし、確認ダイアログで「OK」を選択して --force-with-lease 相当のプッシュを行う（VS Codeは既定でforce-with-lease相当の安全な強制プッシュを行う）
🖱 GitLens拡張機能での操作（右クリック導線・代替手段）

GitLensを導入している場合は、コマンドパレットを使わずマウス操作だけで同じことができます。

  1. 左サイドバーの「GitLens」アイコンから「コミットグラフ (Commit Graph)」を開く（または Ctrl+Shift+G のソース管理ビュー内タブから開く）
  2. グラフ上に表示されている origin/multiBranch_test（リモート追跡ブランチ）を右クリックし、コンテキストメニューから「Fetch」を選び最新化する
  3. 現在のブランチ（dev-b/battery-overvoltage-latch）がチェックアウトされた状態で、グラフ上の origin/multiBranch_test の位置にあるコミットを右クリックし、「Rebase Current Branch onto Commit...」（または「Rebase Current Branch onto Branch...」）を選ぶ
  4. 以降のコンフリクト解消・続行の操作は上記のVS Code標準機能と同じ（ソース管理ビューでCodeLensを使って解消→「続行」）
  5. プッシュも同様にグラフ上の自分のブランチを右クリック→「Push (Force)」で行える
GitLensの利点は、ブランチの分岐・統合の様子をグラフで見ながら右クリックだけで操作できる点です。「今どのコミットに対してrebaseしようとしているか」が視覚的に分かるため、コマンドパレットに慣れていない受講者にはこちらを推奨してもよいでしょう。

5. コンフリクト発生の原理原則（よくある誤解）

誤解1: 「同じファイル・同じ関数を触ったらコンフリクトになる」

半分正解、半分誤解です。 Gitの3-way マージはファイル単位でも関数単位でもなく、行（正確には差分の"ハンク"と、その前後の文脈行）単位で判定します。同じ関数を触っていても、変更箇所が十分離れていれば自動マージされます。

実際に今回のハンズオンでも、開発者A・Bはどちらも battery_evaluate() という同じ関数を変更しましたが、結果は次のように分かれました。

変更箇所Aの変更Bの変更結果
#define の追加位置VREF_MV の直後に1行追加VREF_MV の直後に1行追加（全く同じ行）コンフリクト
if-else チェーンover判定とcritical判定の間に分岐を追加low判定とelseの間に分岐を追加（離れた場所）自動マージ成功
構造体フィールド末尾に hysteresis_active を追加末尾に fault_latched を追加（全く同じ挿入位置）コンフリクト

つまり「同じ関数を触ったから危ない」のではなく、「共通の祖先(merge-base)から見て、両者が全く同じ行・隣接する行を書き換えたかどうか」がコンフリクトの本質的な判定基準です。

誤解2: 「相手の変更が取り込まれていない(out-of-date)状態のPRは、それだけでコンフリクトになる」

誤りです。 「ベースブランチが自分より進んでいる（out-of-date）」ことと、「コンフリクトが発生する」ことは別の現象です。GitHubのPR画面には主に次の2つの状態があり、混同されがちです。
GitHubの表示意味マージ操作
This branch is out-of-date with the base branchベースが進んだが、自分の変更と重なっていない自動マージ可能（コンフリクトなし）。ボタン一つで更新できる
This branch has conflicts that must be resolvedベースの変更と自分の変更が同じ箇所に重なっている手動解消が必須。rebaseまたはmergeで解消してからpush
flowchart TD A["ベースブランチが自分より進んでいる?"] -->|いいえ| B["out-of-date でも conflict でもない"] A -->|はい| C{"自分の変更とベース側の変更が
同じ行・隣接する文脈で重なっているか"} C -->|いいえ| D["out-of-date のみ
自動マージ可能・conflictなし"] C -->|はい| E["コンフリクト発生
手動解消が必須"]

今回のB-1.5のケースで言えば、Bのブランチは「Aのマージ後のmultiBranch_test」に対して out-of-date でした。もしAとBが別々のファイル・別々の行を変更していたら、out-of-dateではあってもコンフリクトにはならず、そのままマージできていたはずです。今回は#defineと構造体フィールドの挿入位置が偶然重なっていたため、out-of-date であることに加えて真のコンフリクトも発生しました。

教訓: 「PRが赤い(out-of-date)＝コンフリクトがある」ではありません。まず git fetch して rebase（または merge）を試み、実際にコンフリクトマーカーが出るかどうかで初めて「本当に重なっているか」が判明します。

🔥 重点解説: 「PRをマージすると、先に進んでいた相手の変更を巻き戻してしまうのでは？」という不安

これは初心者が最も不安に感じやすいポイントです。「自分のブランチは古いコミットから分岐している。そんな古い状態のPRをマージしたら、その後に相手が積んだ変更が消えてしまうのでは？」という懸念ですが、結論から言うと通常の手順（merge / rebase）を踏む限り、相手の変更が消えることはありません。

原理: PRのマージは「古い分岐点」ではなく「ベースの最新コミット」を基準に行われる

GitHubでgh pr mergeやマージボタンを押したとき（あるいはローカルでgit merge/git rebaseしたとき）、Gitが比較するのは次の3点です。

  • 共通の祖先（merge-base）: AとBが分岐した時点のコミット
  • ベースブランチの現在の最新コミット: Aの変更が既にマージされた後のmultiBranch_test
  • 自分のブランチの最新コミット: Bが積んだ変更

マージ結果は「ベースブランチの現在の最新コミットの内容」＋「自分のブランチが merge-base から積み増した差分」の合成になります。ベースブランチを分岐時点まで巻き戻す操作は一切行われません。

gitGraph commit id: "merge-base" branch "dev-b-battery-overvoltage-latch" commit id: "B-change" checkout main commit id: "A-change" commit id: "PR-A-merged" merge "dev-b-battery-overvoltage-latch" id: "PR-B-merged-both-kept"

実際に本ハンズオンでも、開発者Bのブランチは開発者Aのマージ前のコミットから分岐していましたが、PR #7 をマージした後の multiBranch_test には、A由来の HYSTERESIS_MV / hysteresis_active と、B由来の OVERVOLTAGE_LATCH_MARGIN_MV / fault_latched が両方とも残っていることを、実際にビルド・テストで確認済みです。「Bが古い状態から始めた」ことは、最終結果からAの変更が失われる理由にはなりません。

では、本当に相手の変更を消してしまう危険があるのはどんな時か

「out-of-date だから」ではなく、次のような操作ミスがある場合にのみ、相手の変更を消すリスクがあります。ここが本当に注意すべきポイントです。

危険な操作何が起きるか対策
共有ブランチ（multiBranch_testなど）へ古いローカル状態から git push --forceリモートの履歴そのものを、自分の古いローカル履歴で丸ごと上書きしてしまい、相手のコミットが本当に消える共有ブランチにはforce pushしないのが原則。個人のfeatureブランチのみ--force-with-leaseで運用する
コンフリクト解消時に git checkout --ours <file> などで機械的に「自分の版」を採用マーカーの中身を精査せず片側を丸ごと採用すると、相手の変更（このケースではAのヒステリシス処理）がファイルごと消えるコンフリクト解消は必ずマーカーの両側を読み、機能として両立できないか検討してから編集する
相手の変更を取り込まないまま、意図的に古い内容で新しいコミットを作る（例: 手元のバックアップから丸ごと上書き）Gitの3-wayマージの外側で行われる操作なので、単純な「上書きコミット」として消えたように見えるファイルを丸ごと上書きするのではなく、必ず git fetch → rebase/merge のワークフローに乗せる
古いローカルの参照（git reset --hard <古いコミット>）を共有ブランチに force pushローカルでは正しく見えても、実際には相手の最新コミットより古い状態を「正」としてリモートに反映してしまう共有ブランチをリセットする前に必ず git fetch して最新を確認する
まとめ: 「out-of-date な状態でPRを作る／マージする」こと自体は安全です。危険なのは共有ブランチへのforce pushとコンフリクト解消時の不注意な片側採用の2つだけです。この2つさえ避ければ、複数人が並行して作業しても、通常のPRフローで相手の変更が失われることはありません。

もう一つの不安: 「PRのベース（分岐元）が古いこと自体が、マージ先に古い内容を持ち込んでしまうのでは？」

これも非常によくある疑問です。「Bのブランチは、Aがまだ変更する前の古いbattery_monitor.cを土台にしている。そんな“古い土台”を含むBのブランチをマージしたら、その“古さ”がマージ先にも反映されて、Aの新しい変更が古い内容に戻ってしまうのでは？」という懸念です。

結論: なりません。 Gitのマージは「Bのブランチのファイル全体」を持ち込むのではなく、Bのコミットが実際に加えた差分（パッチ）だけをベースの最新版に適用します。Bが触っていない行は、たとえBのローカルコピー上では「古い内容」のままだったとしても、マージ結果には一切影響しません。

具体例で確認する

battery_monitor.cのbattery_evaluate()を例に、3つの時点のファイル内容を比較します。

時点over判定critical/low判定備考
① merge-base（A/B分岐点）if (voltage_mv > ctx->over_threshold_mv)ヒステリシス処理なしAもBもここから分岐
② ベース最新（Aマージ後）over判定はそのままAがヒステリシス処理を追加済みBはまだこの変更を知らない
③ Bのブランチ（分岐時点のまま）Bが過電圧ラッチ処理を追加ヒステリシス処理は①のまま（Bのローカルには存在しない）Bの差分は「ラッチ処理の追加」のみ
④ マージ結果Bが追加したラッチ処理Aが追加したヒステリシス処理（②から継承）Bは③の「ヒステリシス処理がない状態」を持ち込んだのではなく、②の上にBの差分だけを適用

ポイントは③と④の違いです。Bのローカルファイルには実際には「ヒステリシス処理がない、古いbattery_evaluate()」が存在していますが、マージ時にGitが見ているのは「Bが③で何を書き加えたか」という差分だけです。Bが critical/low 判定部分に何も変更を加えていないため、その部分は②（Aの最新版）がそのまま残ります。「Bのファイル全体で上書きする」わけではないため、Aの新しい変更が古い内容に戻ることはありません。

実際に検証してみる

# マージ後のmultiBranch_testに、A由来・B由来の両方の変更が残っているか確認
git show origin/multiBranch_test:src/dbc/battery_monitor.c | grep -n "HYSTERESIS_MV\|OVERVOLTAGE_LATCH_MARGIN_MV"
# => 両方の#defineが出力されれば、どちらの変更も失われていないことが確認できる
唯一の例外: Bが③の時点で、Aが変更したのと同じ行（over/critical判定そのもの）にも手を加えていた場合は、そこはコンフリクトとして手動解消が必要になります（「誤解1」参照）。その場合でも、解消時にマーカーの両側をきちんと読んで両方の変更を反映させれば、古い内容がベースに逆流することはありません。

誤解3: 「同じ行を両者が変更したら必ずコンフリクトになる」

これも厳密には誤解です。両者が全く同じ内容に変更した場合（結果が同一）は、Gitはコンフリクトとして扱わず自動的に1つにまとめます。 コンフリクトになるのは「同じ行（またはその周辺）に対して、互いに異なる変更を加えた」場合だけです。

具体例集: コンフリクトになる例／ならない例（組み込みC開発の早見表）

本リポジトリのコードに沿って、複数人が別々に修正したときにコンフリクトになるパターンとならないパターンを具体例で整理します。判定基準は常に「共通の祖先から見て、同じ行・隣接する文脈を、互いに異なる内容で書き換えたか」です。

❌ コンフリクトになる例

ケースAさんの変更Bさんの変更なぜ競合するか
同じ判定式の閾値変更battery_evaluate()のover_threshold_mv比較を>から>=に変更同じ行の比較演算子はそのままに、値へマージンを追加全く同じ1行を、異なる内容で書き換えている
構造体フィールドの同一挿入位置temp_alarm_fsm_tの末尾にhysteresis_activeを追加同じ末尾にfault_latchedを追加「構造体の最終フィールドの次の行」という同一の挿入位置
同じマクロの再定義Std_Types.hのNULL_PTRマクロの実装を((void*)0)から独自マクロに変更同じNULL_PTR行にAUTOSAR標準の別定義を追加同一マクロの同一行を別内容で編集

✅ コンフリクトにならない例

ケースAさんの変更Bさんの変更なぜ自動マージされるか
別ファイルの変更battery_monitor.cを修正Adc.cを修正そもそもファイルが異なり、比較対象の差分が重ならない
同一ファイル内でも離れた関数battery_monitor.cのbattery_evaluate()を修正同じファイルのbattery_raw_to_mv()を修正変更行が離れていて差分のハンクが重ならない
同じ関数でも離れた分岐（本教材の実例）battery_evaluate()のlow/else間に分岐追加同じ関数のover/critical間に分岐追加行番号が離れており、前後文脈も重ならない
構造体の異なるフィールドを個別に変更battery_monitor_tのlow_threshold_mvの型コメントを修正同じ構造体のover_threshold_mvの型コメントを修正異なる行（フィールド）を個別に編集しており重ならない
全く同じ修正を偶然両者が実施dbc_assert.cのログ出力に同じ1行を追加同じ場所に一字一句同じ1行を追加差分の内容が完全一致するため、Gitは1つの変更として扱う
片方が新規ファイルを追加新規にsrc/dbc/current_monitor.cを追加既存のbattery_monitor.cを修正新規ファイルの追加は既存ファイルの差分と無関係
注意（隣接コンフリクト）: 「離れていれば必ず安全」というわけではありません。Gitの3-wayマージはデフォルトで前後3行の文脈も考慮するため、変更箇所がごく近い（数行以内）場合は、文脈がずれてコンフリクトになることがあります。表内の「離れた分岐」も、閾値によっては近すぎるとコンフリクトになり得る点に注意してください。

6. コンフリクトの読み方と対処

6.1 コンフリクトマーカーの読み方

<<<<<<< HEAD
（リベース先＝multiBranch_test側、つまりA側の変更）
=======
（リベース中のコミット＝B側の変更）
>>>>>>> d4660db (feat: 過電圧ラッチ機能を追加)
記号意味
<<<<<<< HEAD 〜 =======rebase先（今回は更新後の multiBranch_test、Aの変更）
======= 〜 >>>>>>>取り込もうとしている自分のコミット（Bの変更）
🖱 VS Codeでの見え方の対応表

VS Codeのエディタでは、上記のテキストマーカーの代わりに色付きのブロックとインラインボタン（CodeLens）で同じ情報が表示されます。

テキストのマーカーVS Code上の表示
<<<<<<< HEAD の側（rebase先＝Aの変更）緑色の帯「現在の変更 (Current Change)」＋ボタン「現在の変更を承諾」
>>>>>>> の側（取り込み側＝Bの変更）青色の帯「入力側の変更 (Incoming Change)」＋ボタン「入力側の変更を承諾」
両方採用したい場合ボタン「両方の変更を承諾 (Accept Both Changes)」、または手動編集
解消方針: 今回のケースは両者の変更が機能として排他ではないため、両方を残す形（マーカーを削除し、両方の定義・フィールドを併記）で解消します。実務では、どちらか一方が不要になるケースや、両者と相談して設計をすり合わせるケースもあります。

6.2 merge と rebase の違い

git mergegit rebase
履歴マージコミットが残り分岐が見える直線的な履歴になる（書き換え）
コンフリクト解消回数1回にまとまるコミットごとに発生しうる
共有ブランチへの影響安全（履歴を書き換えない）push済みの共有ブランチには要注意
VS Codeでの実行方法ソース管理ビュー「...」→「プル、リベースの代わりにマージ」、または「ブランチのマージ...」コマンドパレット→「Git: Rebase Branch...」
VS Codeのソース管理ビューには、通常の操作（コミット・プッシュ・プル・ブランチ作成）向けの分かりやすいボタンはありますが、rebaseだけは専用ボタンがなく、コマンドパレット（Ctrl+Shift+P）経由の操作になります。「リベースは少し上級者向けの操作」と位置づけられていることを受講者に伝えてください。

6.3 force-push の危険性

危険: git push --force はリモートの履歴を無条件に上書きし、他人が積んだコミットを消してしまう可能性があります。必ず git push --force-with-lease を使い、リモートが自分の想定と異なる場合は失敗させて事故を防ぎましょう。
VS Codeでステータスバーの「同期」表示から強制的にプッシュする場合、設定 git.useForcePushWithLease（既定でtrue）が有効であれば、GUI操作でも自動的に --force-with-lease 相当の安全な強制プッシュが行われます。念のため設定を確認しておくとよいでしょう。

7. 振り返り

  • 同じ関数・同じファイルを複数人で触るときは、事前に役割分担やインターフェースを合わせておくとコンフリクトを減らせる
  • PRは小さく・頻繁に出すほど、コンフリクトの解消コストが下がる
  • 「相手の変更がローカルに反映されていない」状態を避けるには、作業開始前・PR作成前に git fetch ＋ git rebase origin/<base>（または pull --rebase）を習慣化する
  • コンフリクト解消後は必ずビルド・テストを実行し、機械的なマーカー除去だけでなく機能として正しいかを確認する

8. トレーナー向け：再現・配布手順

8.1 演習の起点について（重要）

注意: 本教材の元になった演習（PR #6・#7）は、実際に multiBranch_test へマージ済みです。そのため現在のmultiBranch_testには、開発者A・Bのヒステリシス／過電圧ラッチ処理が既に両方含まれています。同じ内容で全く同じコンフリクトを再現したい場合、multiBranch_testを演習前の状態に force push で巻き戻すことは絶対に行わないでください（共有ブランチへのforce pushは本教材で「危険」と教えている操作そのものです）。

代わりに、演習前の状態を指すタグ handson-git-conflict-baseline（multiBranch_testを書き換えず追加しただけの、非破壊的な参照）を用意しています。再演習する場合はこのタグから分岐してください。

# タグを起点に演習用ブランチを作り直す（multiBranch_test 自体は一切変更しない）
git fetch origin --tags
git checkout -b dev-a/<演習名> handson-git-conflict-baseline
git checkout -b dev-b/<演習名> handson-git-conflict-baseline
# 以降は本編の Step A-1 / Step B-1 と同じ要領で進める（ただし最終PRのbaseは
# multiBranch_test ではなく、演習専用の使い捨てブランチ・使い捨てリポジトリを推奨）
この手順は実際にローカルのみ（trial-main/trial-dev-a/trial-dev-b という使い捨てブランチ、pushなし）で動作確認済みです。タグから分岐 → 両者が同じ挿入位置に別々の変更を追加 → 片方をマージ → もう片方をリベース、で本編と同じ内容のコンフリクトマーカーが再現されました。

8.2 演習環境のリセット（受講者のローカル作業ブランチのみ）

# 受講者ローカルの演習用ブランチを削除して起点に戻す
git checkout multiBranch_test
git branch -D dev-a/battery-hysteresis dev-b/battery-overvoltage-latch
git push origin --delete dev-a/battery-hysteresis dev-b/battery-overvoltage-latch
# multiBranch_test 自体は最新のリモートに追従させるだけ（reset --hard で巻き戻さない）
git fetch origin
git merge --ff-only origin/multiBranch_test
上記はローカル・リモートの演習用feature branchを削除する破壊的操作です。multiBranch_testやmainなど共有ブランチには reset --hard や push --force を行わないでください。実行前に対象ブランチ名を必ず確認してください。

8.3 受講者ごとに独立した演習にする場合

  • 各受講者（ペア）ごとにforkまたは専用ブランチ名（例: dev-a/<name>）を使い分ける
  • 同じmultiBranch_testを共有する場合は、演習前に必ずhandson-git-conflict-baselineタグから分岐し直す

8.4 教材の拡張案（他の組み込み現場ケース）

  • AUTOSAR層（Adc.c / Dio.c）のレジスタ・API変更が競合するケース
  • 割り込みハンドラ（ISR）の追加・変更が同一ファイルで競合するケース
  • ヘッダのマクロ定義変更（例: 閾値定数）とロジック変更が別ブランチで競合するケース
  • リリースブランチへのバックポート時に発生するコンフリクト（cherry-pick演習への拡張）
