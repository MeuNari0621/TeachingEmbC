1. 学習目標

  • featureブランチの作成からPull Request（PR）作成・レビュー・マージまでの一連の流れを体験する
  • 複数人が並行して同じファイルを変更したときにコンフリクトがなぜ・どこで発生するかを理解する
  • git rebase によるコンフリクト解消と、git merge との違いを説明できるようになる
  • git push --force-with-lease の必要性と、単純な --force との危険性の違いを理解する
  • 組み込み開発現場で起きがちな「同一関数のロジック競合」「ヘッダ/構造体定義の競合」「相手の変更がローカルに反映されていない」ケースへの対処を体験する

2. 全体の流れ（ブランチ図）

multiBranch_test を起点に、開発者A・開発者Bがそれぞれ独立したブランチで作業し、Aを先にマージ、Bはリベースでコンフリクトを解消してからマージする流れです。

gitGraph commit id: "multiBranch_test (起点)" branch dev-a/battery-hysteresis branch dev-b/battery-overvoltage-latch checkout dev-a/battery-hysteresis commit id: "Aの実装: ヒステリシス追加" checkout multiBranch_test merge dev-a/battery-hysteresis id: "PR(A)マージ" checkout dev-b/battery-overvoltage-latch commit id: "Bの実装: 過電圧ラッチ追加" commit id: "リベースで競合解消 (force-with-lease push)" checkout multiBranch_test merge dev-b/battery-overvoltage-latch id: "PR(B)マージ"

実際の git rebase はコミット履歴を書き換える操作のため、上図の「リベースで競合解消」はBのブランチの履歴がAのマージ後のmultiBranch_testの上に付け替えられたことを表しています（マージコミットとは異なる仕組みです）。

3. 事前準備

受講者向けチェックリスト

  • リポジトリをclone済みで、multiBranch_test ブランチが最新であること
  • cmake / ninja（または ctest）でビルド・テストが実行できる環境
  • GitHub CLI（gh）またはブラウザでPR操作ができること
  • 1人で演習する場合は「開発者A」「開発者B」の2役を演じる想定（実務では別々の担当者が同時に行う）
重要: 開発者Bのブランチは、開発者Aのマージ前の multiBranch_test から分岐させてください。これにより「相手の変更がローカルに反映されていない」状態を意図的に再現します。

4. ハンズオン手順

開発者A Step A-1: ブランチ作成と実装

git checkout multiBranch_test
git pull
git checkout -b dev-a/battery-hysteresis
# battery_evaluate() にロジックを追加（例: ヒステリシス処理）
# temp_alarm_fsm_t 構造体にフィールドを追加
cmake --build build
ctest --test-dir build --output-on-failure
git add -A
git commit -m "feat: バッテリ評価にヒステリシスを追加"
git push -u origin dev-a/battery-hysteresis

開発者A Step A-2: PR作成・マージ

gh pr create --base multiBranch_test --head dev-a/battery-hysteresis --title "feat: バッテリ評価にヒステリシスを追加（開発者A）"
# レビュー後
gh pr merge <PR番号> --merge

開発者B Step B-1: Aのマージ前に分岐して実装

git checkout multiBranch_test   # Aがマージされる前の状態
git checkout -b dev-b/battery-overvoltage-latch
# battery_evaluate() の同じ判定ロジック付近に別の機能を追加（例: 過電圧ラッチ）
# temp_alarm_fsm_t 構造体の同じ挿入位置に別フィールドを追加
cmake --build build
ctest --test-dir build --output-on-failure
git add -A
git commit -m "feat: 過電圧ラッチ機能を追加"
git push -u origin dev-b/battery-overvoltage-latch
gh pr create --base multiBranch_test --head dev-b/battery-overvoltage-latch --title "feat: 過電圧ラッチ機能を追加（開発者B）"

開発者B Step B-1.5: コンフリクトに気づくタイミング

開発者Bは、この時点ではまだ何もおかしいことに気づいていません。ローカルのビルド・テストは問題なく通り、自分のPR (#7) もエラーなく作成できているためです。気づくきっかけは主に次の2つです。

  1. GitHub PR画面での気づき: 開発者AのPR (#6) がマージされた直後、PR #7 のページを開くと GitHub が自動的に This branch has conflicts that must be resolved（このブランチにはマージ前に解決が必要なコンフリクトがあります）という警告を表示します。これはBが何も操作していなくても、GitHub側がベースブランチ（multiBranch_test）とBのブランチを比較して検知するものです。
  2. ローカルでの気づき: Bがローカルで最新化しようとして git fetch origin を実行し、git status や git log origin/multiBranch_test..HEAD を見ると、自分のブランチが「Aのマージコミットを含まない、分岐したままの状態」であることに気づきます。
体験ポイント: ここで「自分は何も壊していないのに、なぜ急にPRが赤くなるのか？」を実際に確認させてください。原因は自分の変更ではなく、ベースブランチが自分の知らない間に進んでいたことにあります。組み込み開発では「相手の変更に気づかないままローカルで作業を続ける」ことが最も典型的なコンフリクトの温床です。

merge か rebase か、この教材で rebase を選ぶ理由

選択肢内容この教材での採用
git merge origin/multiBranch_testBのブランチに、multiBranch_testを取り込むマージコミットを作る。履歴が分岐したまま残る。他の人ともBブランチを共有している場合はこちらが安全（履歴を書き換えないため）
git rebase origin/multiBranch_testBのコミットを、最新のmultiBranch_testの上に「付け替える」。履歴が一本の直線になり、PRの差分もBの変更だけに見える。採用。Bのブランチは自分専用（他の人がpullしていない）ため、履歴を書き換えても安全。PRのdiffが読みやすくなるメリットを優先
判断基準: そのブランチをまだ自分しか使っていないかがポイントです。誰かが既にpullして作業している共有ブランチをrebaseすると、相手の履歴と食い違い、二次的なコンフリクトを引き起こします。featureブランチのような「個人の作業ブランチ」はrebase、共有ブランチはmergeが基本方針です。

開発者B Step B-2: リベースしてコンフリクト解消を体験する

git fetch origin
git rebase origin/multiBranch_test
# ここでコンフリクトが発生する（Step B-1.5で予告した通り）
git status
# コンフリクトマーカーを手動で解消（次章参照）
git add <解消したファイル>
git rebase --continue
cmake --build build
ctest --test-dir build --output-on-failure
git push --force-with-lease -u origin dev-b/battery-overvoltage-latch

rebase実行直後、ターミナルに
CONFLICT (content): Merge conflict in src/dbc/battery_monitor.c
CONFLICT (content): Merge conflict in src/app/temp_alarm_fsm.h
と表示される瞬間が「実際にコンフリクトに直面する体験」です。git status で both modified: と表示されるファイルが、解消が必要なファイルです。

開発者B Step B-3: PRマージ

gh pr merge <PR番号> --merge

5. コンフリクトの読み方と対処

5.0 コンフリクトは「偶然」ではなく「変更箇所の重なり」で起きる

今回、開発者Aと開発者Bはお互いの実装を見ずに同じ2ファイル（battery_monitor.c / temp_alarm_fsm.h）を変更しました。実務ではよくあることで、コンフリクトは「誰かのミス」ではなく「変更箇所がたまたま重なった」だけで起こります。重要なのは、それにいつ気づき、どう解消するかです（Step B-1.5参照）。

5.1 なぜ「一部は自動マージ」され「一部は競合」するのか

Gitの3-way マージは行単位の差分で判断します。AとBがそれぞれ別の if-else 分岐を「異なる挿入位置」に追加した場合は自動マージされますが、同じ行（例: 同じ場所への#define追加や、構造体の同じ末尾へのフィールド追加）を変更すると競合します。

5.2 コンフリクトマーカーの読み方

<<<<<<< HEAD
（リベース先＝multiBranch_test側、つまりA側の変更）
=======
（リベース中のコミット＝B側の変更）
>>>>>>> d4660db (feat: 過電圧ラッチ機能を追加)
記号意味
<<<<<<< HEAD 〜 =======rebase先（今回は更新後の multiBranch_test、Aの変更）
======= 〜 >>>>>>>取り込もうとしている自分のコミット（Bの変更）
解消方針: 今回のケースは両者の変更が機能として排他ではないため、両方を残す形（マーカーを削除し、両方の定義・フィールドを併記）で解消します。実務では、どちらか一方が不要になるケースや、両者と相談して設計をすり合わせるケースもあります。

5.3 merge と rebase の違い

git mergegit rebase
履歴マージコミットが残り分岐が見える直線的な履歴になる（書き換え）
コンフリクト解消回数1回にまとまるコミットごとに発生しうる
共有ブランチへの影響安全（履歴を書き換えない）push済みの共有ブランチには要注意

5.4 force-push の危険性

危険: git push --force はリモートの履歴を無条件に上書きし、他人が積んだコミットを消してしまう可能性があります。必ず git push --force-with-lease を使い、リモートが自分の想定と異なる場合は失敗させて事故を防ぎましょう。

6. 振り返り

  • 同じ関数・同じファイルを複数人で触るときは、事前に役割分担やインターフェースを合わせておくとコンフリクトを減らせる
  • PRは小さく・頻繁に出すほど、コンフリクトの解消コストが下がる
  • 「相手の変更がローカルに反映されていない」状態を避けるには、作業開始前・PR作成前に git fetch ＋ git rebase origin/<base>（または pull --rebase）を習慣化する
  • コンフリクト解消後は必ずビルド・テストを実行し、機械的なマーカー除去だけでなく機能として正しいかを確認する

7. トレーナー向け：再現・配布手順

7.1 演習環境のリセット

# ローカルの演習用ブランチを削除して起点に戻す
git checkout multiBranch_test
git branch -D dev-a/battery-hysteresis dev-b/battery-overvoltage-latch
git push origin --delete dev-a/battery-hysteresis dev-b/battery-overvoltage-latch
# 起点ブランチを最新化
git fetch origin
git reset --hard origin/multiBranch_test
上記はローカル・リモートのブランチを削除する破壊的操作です。実行前に対象ブランチ名を必ず確認してください。

7.2 受講者ごとに独立した演習にする場合

  • 各受講者（ペア）ごとにforkまたは専用ブランチ名（例: dev-a/<name>）を使い分ける
  • 同じmultiBranch_testを共有する場合は、演習前に必ずリセット手順を実施してから開始する

7.3 教材の拡張案（他の組み込み現場ケース）

  • AUTOSAR層（Adc.c / Dio.c）のレジスタ・API変更が競合するケース
  • 割り込みハンドラ（ISR）の追加・変更が同一ファイルで競合するケース
  • ヘッダのマクロ定義変更（例: 閾値定数）とロジック変更が別ブランチで競合するケース
  • リリースブランチへのバックポート時に発生するコンフリクト（cherry-pick演習への拡張）
